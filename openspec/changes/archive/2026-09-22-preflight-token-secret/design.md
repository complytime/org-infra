## Context

`reusable_release_preflight.yml` creates annotated tags via the GitHub API in its
"Create and push tag" step. The step currently authenticates with `GITHUB_TOKEN`.
GitHub's anti-recursion rule silently drops events generated by `GITHUB_TOKEN`, so
any downstream tag-triggered workflow (e.g., container publish) never fires.

The org already handles this pattern in `reusable_publish_ghcr.yml`, where the
`org_check_token` optional secret falls back to `GITHUB_TOKEN` when not provided.

## Goals / Non-Goals

**Goals:**

- Allow callers to provide an elevated token that creates tags capable of
  triggering downstream workflows.
- Scope the elevated token to the single tag-creation step, preventing privilege
  creep to other steps.
- Preserve identical behavior for callers that don't pass the secret.

**Non-Goals:**

- Enforcing token type (PAT vs. GitHub App token) — org-level policy concern.
- Changing inputs, outputs, permissions, concurrency, or adding steps/jobs.
- Auto-syncing the workflow to other repos (not in `sync-config.yml`).

## Decisions

### Decision 1: Optional secret with GITHUB_TOKEN fallback

**Chosen**: Add `secrets.tag_push_token` (required: false) and use the expression
`secrets.tag_push_token != '' && secrets.tag_push_token || secrets.GITHUB_TOKEN`
in the tag step's `env:` block.

**Alternatives considered:**

- **Require the secret** — breaks all existing callers that don't need downstream
  triggering. Rejected.
- **Job-level `env:` with the token** — every step (including CI verification)
  would inherit the elevated token. Rejected for unnecessary privilege exposure.
- **New input parameter (not a secret)** — tokens must not appear in workflow logs.
  Inputs are not masked. Rejected.

**Rationale:** Matches the established `org_check_token` pattern in
`reusable_publish_ghcr.yml`. Optional secrets with `!= ''` guard are the standard
GitHub Actions idiom for fallback behavior since `secrets.<name>` evaluates to
empty string when not provided.

### Decision 2: Step-level scoping only

**Chosen**: Set `GH_TOKEN` via `env:` on the "Create and push tag" step only.

**Alternatives considered:**

- **Job-level `env:`** — leaks the elevated token to all steps. Rejected.
- **Workflow-level `env:`** — same problem, worse scope. Rejected.

**Rationale:** Follows least-privilege. Future steps added to the workflow default
to `GITHUB_TOKEN` without the author needing to know about the elevated token.

### Decision 3: Warn about recursive triggering in the secret description

**Chosen**: Include a warning in the `description:` field of the secret about
infinite loops when downstream workflows also create tags with elevated tokens.

**Alternatives considered:**

- **Runtime detection of recursive triggers** — no reliable mechanism in GitHub
  Actions to detect the token source of an upstream event. Rejected as infeasible.
- **No warning** — callers might not realize the risk. Rejected.

**Rationale:** The description is the only documentation surface visible at the
`workflow_call` declaration site. It is the right place for caller-facing guidance.

## Risks / Trade-offs

### Risk: Recursive workflow triggering

If a downstream workflow triggered by the new tag also creates tags using an
elevated token, infinite loops can occur. **Mitigation:** The secret description
warns callers. Org admins can audit which repos pass elevated tokens via GitHub
audit logs.

### Risk: Elevated token exposure surface

Accepting an external token widens the trust boundary. A compromised caller token
could push arbitrary tags. **Mitigation:** Step-level scoping limits exposure to
the single tag-creation step. Token policy (PAT restrictions, approval gates) is
enforced at the org level, not in the workflow.

### Trade-off: No token-type validation

The workflow does not verify whether the provided token is a GitHub App token or a
PAT. This keeps the workflow simple but relies on org policy for enforcement.
